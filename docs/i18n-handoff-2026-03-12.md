## 高风险点

### 1. 页面级改动较多，但没有跑编译

这轮涉及 `useI18n()`、`t()`、资源 key、Provider、store 类型，任何一个 key 拼错都可能在编译期或运行期暴露。

重点检查：

- `src/pages/myApps/**`
- `src/pages/ranking/index.tsx`
- `src/hooks/useLinglongProcesses.ts`
- `src/hooks/useAppInstall.ts`
- `src/hooks/useAppUninstall.ts`

### 2. 当前实现是轻量 i18n，不是第三方库

这是有意设计，不是漏装依赖。

接手时不要误判成“少装了 `i18next`”。  
如果未来要切换到 `i18next`，建议复用：

- `useI18n()`
- `translate()`
- `getCurrentLocale()`
- `TranslationKey`

避免再次全仓替换业务调用面。

### 3. `appDisplay.ts` 是后续远端多语言的扩展位

不要回退成组件里到处写：

```ts
app.zhName || app.name || app.appId
```

后续远端 API 一旦区分语言字段，扩展应该收口在：

- `src/utils/appDisplay.ts`

### 4. 列表缓存后续必须考虑 locale

本轮只先把请求头和 UI 边界铺好，还没有改 `src/services/appListCache/` 的 locale 维度。

如果下一位继续推进“远端应用元数据多语言”，必须同步修改缓存 key。

## 可以直接复用的 grep / 排查命令

查旧 key / 历史命名残留：

```bash
rg -n "app\\.name|app\\.logoAlt|layout\\.launch\\.|layout\\.titlebar\\.quitModal|setting\\.base\\.|common\\.language\\." src
```

查翻译调用：

```bash
rg -o "(?:t|translate)\\('([^']+)'" -r '$1' src | sort -u
```

查剩余明显中文硬编码：

```bash
rg -n "\"[^\"]*[\\x{4e00}-\\x{9fa5}][^\"]*\"|'[^']*[\\x{4e00}-\\x{9fa5}][^']*'" src
```
