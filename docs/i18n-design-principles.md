# i18n 架构设计理念说明

## 文档目的

本文档不重复描述“具体改哪些文件”，而是专门说明这套 i18n 架构背后的设计理念、边界划分、工程取舍和后续演进原则。

适用对象：

- 后续继续推进 i18n 的开发者
- 需要评审这套方案是否适合长期维护的人
- 将来接手“远端应用元数据多语言”或“缓存分语言维度”工作的开发者

## 为什么这次 i18n 不能只做字符串替换

这个项目的问题，不是“中文字符串太多”这么简单，而是用户可见文案分布在多个层级：

- 页面 JSX
- 组件静态配置
- hooks 内的 `message` / `Modal.confirm`
- 请求层错误提示
- Ant Design 自带组件 locale
- 远端返回的应用名称、描述、分类等业务数据

如果只是把 JSX 里的中文替换成 `t('...')`，会留下三个长期问题：

1. hooks 和副作用里的提示文案仍然是散的
2. Ant Design 组件语言与业务文案语言不一致
3. 应用元数据会被误当成静态翻译资源，最终导致缓存串语言、维护责任混乱

所以这次设计的重点不是“翻译函数接进去”，而是先把文案治理结构搭起来。

## 这套设计的核心理念

## 1. 把 i18n 当成架构问题，而不是页面问题

国际化不是某个页面的局部能力，而是应用级基础设施。

这意味着：

- 语言偏好必须有统一状态源
- 根入口必须统一初始化
- Ant Design locale 必须在根层同步
- 业务层不能各自决定“当前语言是什么”

因此本轮的第一优先级不是页面翻译，而是：

- `src/stores/appConfig.ts`
- `src/i18n/`
- `src/providers/AppProviders.tsx`
- `src/main.tsx`

先稳定入口，再迁移页面，后面才不会返工。

## 2. 界面文案和业务数据必须分层

这是整套方案里最关键的原则。

### 界面文案

指的是：

- 按钮
- 标题
- 空状态
- tooltip
- `message`
- `Modal.confirm`
- 表格列名
- 设置项说明

这类文案属于前端静态资源，应统一放在：

- `src/i18n/resources/`

### 业务数据

指的是：

- 应用名称
- 中文名 / 英文名
- 描述
- 分类名
- 截图语言
- 远端返回的说明文本

这类内容本质上是服务端业务数据，不应写进静态资源字典。

因此当前单独抽出：

- `src/utils/appDisplay.ts`

它的职责不是“翻译”，而是“展示字段选择与回退”。

这个边界很重要，因为一旦未来远端接口开始按语言返回内容，就必须：

- API 层带 `Accept-Language`
- 缓存 key 带 locale
- 展示层按 locale 选择字段

而不是让前端翻译资源去“伪装”业务内容。

## 3. 单一入口优先，避免多点初始化

这类桌面应用最怕“每层都做一点语言处理”，最后没人知道真实语言状态从哪里来。

所以本方案坚持三件事：

1. 语言偏好只存一份：`useConfigStore.languagePreference`
2. 当前渲染语言只从 i18n 层解析
3. Ant Design locale 只在 `AppProviders` 挂一次

这样做的收益：

- 排查问题时路径明确
- 语言切换时行为一致
- 页面和 hooks 不需要关心系统语言解析细节

## 4. 优先做“可治理的结构”，再做“覆盖率”

一次性把全仓库所有中文替完，不等于这套方案能长期维护。

真正重要的是：

- key 命名是否稳定
- 文案是否按领域分组
- hooks 是否被纳入治理
- 配置和 Provider 是否统一
- 业务数据是否和静态文案分层

所以这轮优先做的是：

- 基础设施
- 高流量壳层
- 高风险 hooks
- 下载 / 安装 / 卸载 / 进程这类提示密集区域

剩余页面后续再补，风险更可控。

## 5. 类型约束优先于运行时炫技

当前实现没有直接引入 `i18next`，而是用了仓库内轻量 typed i18n 层。

这不是为了“省事”，而是基于当前仓库状态做的工程取舍：

- 现在最急的是统一入口和治理结构
- 资源量还没大到必须上复杂运行时
- 项目本身已经是严格 TypeScript
- 当前更需要 key 约束和可控迁移，而不是复杂 ICU 功能

因此当前方案优先提供：

- `TranslationKey`
- `useI18n()`
- `translate()`
- `resolveLocale()`
- `getAntdLocale()`

如果未来真的需要更复杂能力，例如：

- 复数规则
- 富文本翻译
- 翻译平台同步
- 更复杂的 locale fallback

再替换底层运行时即可，业务调用面尽量保持不动。

## 为什么语言偏好存“system”而不是只存具体 locale

桌面应用和普通网页不一样，用户很自然地期待“跟随系统”。

如果只存：

- `zh-CN`
- `en-US`

会立刻出现两个问题：

1. 用户切换系统语言后，应用不会跟着变
2. 设置页没法表达“恢复默认语言策略”

因此 store 存的是：

```ts
type LanguagePreference = 'system' | 'zh-CN' | 'en-US'
```

而真正参与渲染的是 `resolvedLocale`。

这使得“用户偏好”和“最终渲染语言”解耦，长期维护更稳。

## 为什么 hooks 必须纳入 i18n 范围

这类项目里，很多真正的用户提示并不写在页面里，而是写在：

- 安装 hook
- 卸载 hook
- 进程管理 hook
- 更新检查 hook
- 启动初始化 hook

如果只改 JSX，不改 hooks，会出现非常典型的问题：

- 页面是英文
- 弹窗还是中文
- `message.success` / `message.error` 仍然是中文

这会直接破坏语言一致性。

所以本方案把 hooks 看成一等迁移对象，而不是“最后顺手改一下”。

## 为什么菜单配置也必须存 key 而不是存文本

像侧边栏、tab、静态 action 配置，如果继续这样写：

```ts
{ label: '推荐' }
```

即使页面已经接入了 i18n，配置层仍然会把硬编码重新带回来。

因此静态配置应改为：

```ts
{ labelKey: 'layout.sidebar.recommend' }
```

这背后的原则是：

- 配置表达结构
- 资源表达文案

不要把两者混在一起。

## 为什么请求层要提前加 `Accept-Language`

本轮虽然还没有把远端应用元数据正式切到多语言协议，但请求层已经加了：

- `Accept-Language`

原因不是“现在立刻就要用”，而是提前给未来的 API 协商能力留出稳定入口。

这样后续如果远端接口支持：

- 返回不同语言的应用名
- 返回不同语言的描述
- 返回不同语言的分类或说明

前端不需要再到各业务页临时补语言参数，而是继续从统一请求层延伸。

## 为什么缓存必须提前考虑 locale 维度

这是未来很容易踩坑的一点。

如果某个应用列表缓存 key 只有：

- 仓库名
- 架构
- 分类
- 排序

而没有 locale，那么会出现：

- 中文界面先缓存中文应用描述
- 英文界面直接复用中文缓存

最终用户看到的就是“UI 是英文，列表内容还是中文”。

所以这里的原则必须先写清楚：

只要远端应用元数据开始按语言返回，`src/services/appListCache/` 的 key 就必须显式带 locale。

## Rust 与前端 i18n 的边界

当前 Rust 侧为了稳定解析 `ll-cli`，仍然保持英文 locale，这个决策是合理的。

原因是 Rust 侧面对的是“外部命令输出解析稳定性”，前端面对的是“用户界面显示语言”。

两者不是一个问题域。

因此本方案明确要求：

- Rust 继续保证命令解析稳定
- 前端负责把用户可见提示做本地化
- 不要把 `stderr` 原文直接当成最终界面翻译

如果未来要优化错误体验，更好的方向是：

- Rust 返回更稳定的错误码 / 错误分类
- 前端按错误码映射本地化文案

## 这套架构长期维护时应坚持的规则

### 1. 新增静态界面文案时

- 必须先加 key
- 禁止直接写中文到 JSX / hook / message

### 2. 新增业务提示时

- 组件内优先用 `useI18n()`
- 组件外辅助函数可用 `translate()`，但不要扩散成全局随意调用

### 3. 新增应用展示字段逻辑时

- 优先收口到 `src/utils/appDisplay.ts`
- 禁止组件里继续拼 `zhName || name || appId`

### 4. 新增远端列表缓存时

- 如果数据与语言相关，cache key 必须考虑 locale

### 5. 新增第三方组件 locale 处理时

- 优先挂在根层 Provider
- 不在页面层零散初始化

## 后续演进路线

### Phase 1

继续补齐剩余页面硬编码文案，先把全仓库高频用户可见文案收敛完。

### Phase 2

梳理远端 API 的语言能力：

- 是否已有 `lang/lan`
- 是否只支持 `Accept-Language`
- 哪些字段是语言相关的

### Phase 3

给列表缓存增加 locale 维度，并扩展 `appDisplay.ts`。

### Phase 4

如果未来出现更复杂翻译需求，再考虑替换为更重的运行时方案，但保持业务调用面稳定。

## 最终结论

这套 i18n 方案的核心，不是“把中文翻成英文”，而是建立一套长期可治理的文案架构。

它解决的是四个问题：

1. 语言入口统一
2. 静态文案和业务数据分层
3. hooks / 配置 / AntD locale 一起纳入治理
4. 为远端多语言和缓存语言隔离提前铺路

如果后续有人继续在组件里直接写中文、在页面里手动判断 `zhName || name`、或在缓存层忽略 locale，这套架构就会重新退化回不可维护状态。

所以真正需要被继承的，不只是 `t()` 的写法，而是这些边界和原则。
